    18.3: Using Bitcoin with MuSig2

    As demonstrated in the previous section, signing with Schnorr is easy. But what about signing Schnorr multisigs? There are at the moment three main ways to do so: FROST and MuSig2 can be seamlessly integrated into a Bitcoin transaction, but aren't seamlessly integrated into Bitcoin Core. Instead, Bitcoin Core depends on its Merkle trees for multisigs. This section and the next cover FROST and MuSig2, while the next chapter includes discusison of MAST multisigs.

    Understand MuSig2

    Bitcoin multisigs can't be naively created using Schnorr. If you just aggregate two keys, it's possible to cancel out one of the keys (provided you know the public key you're cancelling) and then sign with the other key. To resolve this requires a more complex protocols. One of these is MuSig2.

    MuSig2 is a multisig method (n of n), not a threshold method (m of n). That means that, by default, all of the participants in a MuSig2 signature must sign. The only current methodology for using MuSig2 to create a threshold signature is to create a MAST that lays out each of the possibilities, as briefly mentioned in §19.2.

    Create a MuSig2 Address

    Creating a MuSig2 multisig address requires largely the same methodology as demonstrated in §7.2, except this time we're going to generate it from two different wallets, not two different machines.

    bitcoin-cli createwallet musig1

| {
|   "name": "musig1"
| }

bitcoin-cli createwallet musig2

| {
|   "name": "musig2"
| }

    ℹ️ Multi Multisig Methods. Multisigs should really be generated from different private keys held on different devices. This simplified multi-wallet methodology is used only to make it easier for you to follow along, without having to spin up a second machine.

    As usual, you will extract addresses and public keys from each wallet:

    musigaddress1=$(bitcoin-cli -rpcwallet=musig1 getnewaddress)
musigpubkey1=$(bitcoin-cli -rpcwallet=musig1 -named getaddressinfo address=$musigaddress1 | jq -r '.pubkey')

musigaddress2=$(bitcoin-cli -rpcwallet=musig2 getnewaddress)
musigpubkey2=$(bitcoin-cli -rpcwallet=musig2 -named getaddressinfo address=$musigaddress2 | jq -r '.pubkey')

    You can then use the "tr(musig(...))" descriptor, to denote this address as a MuSig2 Taproot address, when combining these public keys.

    musigdesc="tr(musig($musigpubkey1,$musigpubkey2))"
musigcs=$(bitcoin-cli getdescriptorinfo $musigdesc | jq -r '.checksum')
musigdescwithcs=$musigdesc#$musigcs

    Finally, you'll create a third, watchonly account, to store the MuSig2 descriptor (and allow you to monitor the address).

    bitcoin-cli createwallet "musigwatchonly" true true

| {
|   "name": "musigwatchonly"
| }

bitcoin-cli -rpcwallet=musigwatchonly importdescriptors '''[{ "desc": "'$musigdescwithcs'", "timestamp": "now" }]'''

| [
|   {
|     "success": true
|   }
| ]

    Now you just need your address:

    bitcoin-cli -rpcwallet=musigwatchonly getaddressesbylabel ""

| {
|   "tb1plj6kpu6mw7pd0jngwaz6555aehjudg05reh2jy2mjq0quyuzyvjsfkhw57": {
|     "purpose": "receive"
|   }
| }

    As soon as you send funds to that address, you'll officially have Bitcoin assets locked with a MuSig2 signature.

    The question will be how to retrieve them!

    Spend from a MuSig2 Address

    As we saw in §8.1, the best way to spend a multisig is through a PSBT. That's the case for MuSig2 multisigs as well.

    The process of spending the funds therefore start with the creation of a PSBT. As before, we're going to send the money from the multisig address to the two creators of the multisig.

    split1=$(bitcoin-cli -rpcwallet=musig1 getnewaddress)
split2=$(bitcoin-cli -rpcwallet=musig2 getnewaddress)

utxo_txid=$(bitcoin-cli -rpcwallet=musigwatchonly listunspent | jq -r '.[0] | .txid')
utxo_vout=$(bitcoin-cli -rpcwallet=musigwatchonly listunspent | jq -r '.[0] | .vout')

psbt=$(bitcoin-cli -named createpsbt inputs='''[ { "txid": "'$utxo_txid'", "vout": '$utxo_vout' } ]''' outputs='''{ "'$split1'": 0.0029,"'$split2'": 0.0029 }''')

    Load the Multisig Info

    Our old friend analyzepsbt says that the next thing required is the updater.

    bitcoin-cli analyzepsbt $psbt

|       "is_final": false,
|       "next": "updater"
|     }
|   ],

    Using walletprocesspsbt on the readonly wallet should load the UTXO.

bitcoin-cli analyzepsbt $psbt

This is expected to improve, so some of these analyzepsbt results will likely be different in the future.

    What's going on?

    The two major Schnorr multisig protocols, MuSig2 and FROST, are both multiround protocols. That means that each participant provides some information, it's sent around to the other participants, and only then can they create a final signature.

    For MuSig2, in the first round, each participant offers a "pubnonce": essentially a bit of randomness that sort of fills the role of a public key. In the second round, they then sign using their private nonce and their private key. Those signature shares are then combined to produce the final signature.

    You've conducted the first round of the MuSig2 protocol, and acquired the nonces, but another round is required to acquire the signatures.

    Round 2 of Signing

    You send your combined PSBT around to everyone to process again, this time actually acquiring signatures:

    sig1b=$(bitcoin-cli -rpcwallet="musig1" walletprocesspsbt $psbt_round1 | jq -r '.psbt')
sig2b=$(bitcoin-cli -rpcwallet="musig2" walletprocesspsbt $psbt_round1 | jq -r '.psbt')
psbt_round2=$(bitcoin-cli combinepsbt '''["'$sig1b'", "'$sig2b'"]''')

    Summary: Using Bitcoin with MuSig2

    Bitcoin Core supports MuSig2, but the lack of proper analysis makes it unintuitive to use. Still, the overall process is simple once you get to know it: fill in the UTXO; have each signer process to provide a nonce; combine the PSBTs; have each signer process again to sign; combine the PSBTs again; and send.

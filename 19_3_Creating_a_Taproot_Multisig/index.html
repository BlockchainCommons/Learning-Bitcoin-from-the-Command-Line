    19.3: Creating a Taproot Multisig

    Taproot multisigs can be easily created using descriptors. Doing so reveals the full power of Taproot addresses.

    Understand a Taproot Multisig Descriptor

    BIP 387 defines two Taproot multisig descriptors, multi_a and sortedmulti_a. Their arguments take the form (threshold,key1,key2,...). They differ from multi and sortedmulti because they produce Tapscript for use in a MAST.

    As described in BIP 387, the multisig will be created using the OP_CHECKSIGADD method described in the previous section, not one of the more complex methodologies made possible by the MAST.

    Create a Taproot Multisig Descriptor

    The multi_a and sortedmulti_a descriptors both define script paths. To include them in a tr() descriptor, you therefore use the format tr(KEY,TREE) as also discussed in the previous section.

    You could put a lot of different things in the required key path, including an unspendable key path if you only want the scriptpath to apply. But in this situation we're going to take full advantage of the tr(KEY,TREE) format to allow funds to be spendable either by a single key or a multisig of 2-of-3 keys. Doing so displays the full power of Taproot.

    As it happens, we already have an example that does exactly that, the excutives example laid out using Bitcoin Script in §15.2 and Miniscript in §16.4. We're going to turn it into a real address here, where either one president or two out of three vice-presidents can spend from their multisig address.

    The first thing you need to do is create wallets for all four participants (or in a real situation, have them each working on a different machine).

    bitcoin-cli createwallet "prez"

| {
|   "name": "prez"
| }

bitcoin-cli createwallet "vp1"

| {
|   "name": "vp1"
| }

bitcoin-cli createwallet "vp2"

| {
|   "name": "vp2"
| }

bitcoin-cli createwallet "vp3"

| {
|   "name": "vp3"
| }

    You then collect the public keys for addresses in each of the wallets, a technique that you've used multiple times before.

    prezaddr=$(bitcoin-cli -rpcwallet=prez getnewaddress)
prezpk=$(bitcoin-cli -rpcwallet=prez -named getaddressinfo address=$prezaddr | jq -r '.pubkey')

vp1addr=$(bitcoin-cli -rpcwallet=vp1 getnewaddress)
vp1pk=$(bitcoin-cli -rpcwallet=vp1 -named getaddressinfo address=$vp1addr | jq -r '.pubkey')

vp2addr=$(bitcoin-cli -rpcwallet=vp2 getnewaddress)
vp2pk=$(bitcoin-cli -rpcwallet=vp2 -named getaddressinfo address=$vp2addr | jq -r '.pubkey')

vp3addr=$(bitcoin-cli -rpcwallet=vp3 getnewaddress)
vp3pk=$(bitcoin-cli -rpcwallet=vp3 -named getaddressinfo address=$vp3addr | jq -r '.pubkey')

    Now you can create your descriptor in the form tr(KEY,TREE) which in this case will be tr(PREZ-KEY,sortedmulti_a(THRESHOLD,VP-KEYS...)).

    tapdesc="tr($prezpk,sortedmulti_a(2,$vp1pk,$vp2pk,$vp3pk))"
tapcs=$(bitcoin-cli getdescriptorinfo $tapdesc | jq -r '.checksum')
tapdescwithcs=$tapdesc#$tapcs

    As usual, you also create a watchonly wallet to store the descriptor and extract your multisig address.

    bitcoin-cli createwallet "prezwatchonly" true true

| {
|   "name": "prezwatchonly"
| }

bitcoin-cli -rpcwallet=prezwatchonly importdescriptors '''[{ "desc": "'$tapdescwithcs'", "timestamp": "now" }]'''

| [
|   {
|     "success": true
|   }
| ]

bitcoin-cli -rpcwallet=prezwatchonly getaddressesbylabel ""

| {
|   "tb1pttvmdfpws9mh8874mrcqnkfx67yqw3507g5m7ja2f9c7x9z7ju2qnl8csv": {
|     "purpose": "receive"
|   }
| }

    Prepare the PSBT

    At this point either the president should be able to sign with the single-sig key path or two of the vice presidents should be able to sign with the multisig script path.

    But, does it work?

    We'll try it both ways, using the following PSBT, which sends all the money to the president alone.

    utxo_txid=$(bitcoin-cli -rpcwallet=prezwatchonly listunspent | jq -r '.[0] | .txid')
utxo_vout=$(bitcoin-cli -rpcwallet=prezwatchonly listunspent | jq -r '.[0] | .vout')

abscond=$(bitcoin-cli -rpcwallet=prez getnewaddress)

psbt=$(bitcoin-cli -named createpsbt inputs='''[ { "txid": "'$utxo_txid'", "vout": '$utxo_vout' } ]''' outputs='''{ "'$abscond'": 0.00195 }''')

    As usual, the first thing that's needed is to add the information about the UTXO to the PSBT, which you can do from the watchonly wallet with the descriptor.

    psbt=$(bitcoin-cli -rpcwallet="prezwatchonly" walletprocesspsbt $psbt | jq -r '.psbt')

    analyzepsbt shows that the UTXO is added, but that there are no signatures.

    bitcoin-cli analyzepsbt $psbt

| {
|   "inputs": [
|     {
|       "has_utxo": true,
|       "is_final": false,
|       "next": "updater"
|     }
|   ],
|   "estimated_vsize": 99,
|   "estimated_feerate": 0.00050505,
|   "fee": 0.00005000,
|   "next": "updater"
| }

    The President Signs

    One possibility is that the president signs on his own:

    prezpsbt=$(bitcoin-cli -rpcwallet="prez" walletprocesspsbt $psbt | jq -r '.psbt')

    One signature, and it's ready to go!

    bitcoin-cli analyzepsbt $prezpsbt

| {
|   "inputs": [
|     {
|       "has_utxo": true,
|       "is_final": true,
|       "next": "extractor"
|     }
|   ],
|   "fee": 0.00005000,
|   "next": "extractor"
| }

    Finalization gives you the hex to broadcast.

    bitcoin-cli finalizepsbt $prezpsbt

    The VPs Sign

    The other option is that two VPs sign:

    vp1psbt=$(bitcoin-cli -rpcwallet="vp1" walletprocesspsbt $psbt | jq -r '.psbt')
vp2psbt=$(bitcoin-cli -rpcwallet="vp2" walletprocesspsbt $psbt | jq -r '.psbt')

    Looking at the PSBTs, we see neither is ready to go (which is what we expect!).

    bitcoin-cli analyzepsbt $vp1psbt

| {
|   "inputs": [
|     {
|       "has_utxo": true,
|       "is_final": false,
|       "next": "updater"
|     }
|   ],
|   "estimated_vsize": 99,
|   "estimated_feerate": 0.00050505,
|   "fee": 0.00005000,
|   "next": "updater"
| }

bitcoin-cli analyzepsbt $vp2psbt

| {
|   "inputs": [
|     {
|       "has_utxo": true,
|       "is_final": false,
|       "next": "updater"
|     }
|   ],
|   "estimated_vsize": 99,
|   "estimated_feerate": 0.00050505,
|   "fee": 0.00005000,
|   "next": "updater"
| }

    Instead we have to combine them and then we're ready for the finalizer.

    vppsbt=$(bitcoin-cli combinepsbt '''["'$vp1psbt'", "'$vp2psbt'"]''')

bitcoin-cli analyzepsbt $vppsbt

| {
|   "inputs": [
|     {
|       "has_utxo": true,
|       "is_final": false,
|       "next": "finalizer"
|     }
|   ],
|   "fee": 0.00005000,
|   "next": "finalizer"
| }

    With that final step, you again get your hex for broadcast.

    Summary: Creating a Taproot Multisig

    A Taproot multisig can be created with the multisig_a or sortedmultisig_a descriptors. But that's just the script path and each Taproot script path must be linked to a key path, which offers an alternate way to unlock the transaction.

    A Taproot multisig therefore doesn't just show another way to create multisigs. It also displays the full power of Taproot, which will only increase in the future as it achieves greater usage.
